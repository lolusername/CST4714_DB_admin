Performance Tuning & Optimization
Index Strategy

• Use compound indexes to support your queries; follow the ESR rule (Equality, Sort, Range).
• Avoid over‑indexing and unused indexes.


Query Optimization

• Use explain() to analyse query plans and ensure indexes are being used.
• Avoid unbounded sorting and skip operations on large collections.


Data & Storage

• Keep documents small (less than 16 MB).
• Use compression and allocate enough RAM for your working set.
• Place journal and data files on separate disks to reduce contention.


Scaling & Monitoring

• Use replication to distribute reads and sharding to scale writes.
• Monitor metrics (CPU, memory, I/O, connections) via Atlas or open‑source tools.
• Periodically review slow queries and update indexes accordingly.

CRUD Operations
Create

Use insertOne() or insertMany() to add documents. Collections are created automatically when you insert a document.


Read

Use find() to query documents. You can filter using operators (e.g., $gt, $in) and projection to return specific fields.


Update

Use updateOne(), updateMany() or replaceOne() to modify documents. Updates are atomic at the document level and support operators like $set and $inc.


Delete

Use deleteOne() or deleteMany() to remove documents. Always provide a filter to avoid deleting entire collections.

Why Indexes Matter

Indexes support efficient query execution by allowing MongoDB to scan a subset of documents rather than the entire collection. They use a B‑tree structure and come with write overhead and disk usage costs. Define compound indexes in the order of equality, sort and range (ESR rule), and prefer covered queries where all fields are part of the index.

Schema Design & Best Practices
• Design for your queries: 
Model your documents around the queries your application performs most often. Two applications with identical data may require different schemas.
• Embed vs reference: 
Embed related data if you always fetch it together; reference using document IDs when relationships are many‑to‑many or data is frequently updated.
• Index thoughtfully: 
Use compound indexes following ESR, avoid indexing low‑cardinality fields alone, and leverage partial, sparse, TTL and text indexes where appropriate.
• Keep the working set in memory: 
Ensure that your frequently accessed data fits into RAM to minimise disk I/O. Scale up RAM or use sharding to distribute the load.
• Use replication & sharding: 
Replica sets provide redundancy and read scalability; sharding partitions data across clusters to handle write volume and storage growth.
Additional Tips

- Normalise or denormalise based on access patterns.
- Avoid unbounded arrays; split large arrays into separate collections.
- Precompute values and store them if queries require complex transformations.
- Use capped collections for log‑like data and TTL indexes for volatile data.

Transactions & ACID
ACID Properties

Atomicity: All or nothing – operations within a transaction either commit together or roll back.
Consistency: Data must transition from one valid state to another, enforced by schema and application logic.
Isolation: Concurrent transactions should not interfere; MongoDB provides snapshot isolation using document‑level locks.
Durability: Committed data persists through crashes via journaling and replication.

Multi‑document transactions were introduced in MongoDB 4.0 for replica sets and in 4.2 for sharded clusters. They enforce ACID across multiple operations and collections, using two‑phase commit underneath.

Replica Set Features

• One primary receives all writes; secondaries replicate the primary’s oplog asynchronously.
• Automatic failover: if the primary fails, an election selects a new primary.
• Replication provides redundancy and enables read scaling via read preferences.
• Heartbeats monitor node availability and detect failures.
Replication Lag

Secondaries replicate the primary’s oplog asynchronously, which can create lag. Monitor replication lag via the replication metrics and tune network throughput and write concern accordingly. Read preferences can direct reads to secondaries for load balancing, but stale reads may occur.

Why Shard?

Vertical scaling has practical limits; horizontal scaling divides data across servers. Sharding distributes collections into chunks based on a shard key and balances them across shards.

Components

• Shards: replica sets that store data.
• Config servers: store cluster metadata and the routing table.
• mongos routers: route client queries to appropriate shards.
Shard Keys & Balancing

Choose a shard key that distributes writes evenly. The balancer monitors chunk sizes and migrates chunks to keep shards balanced. Sharding increases capacity for write throughput and storage while maintaining high availability.

Backup & Restore
Backup Strategies

• mongodump/mongorestore: Suitable for small to medium deployments; dumps BSON to files.
• Cloud Manager / Ops Manager: Provides continuous backup, incremental snapshots and point‑in‑time restores.
• Filesystem snapshots: Use LVM or storage‑layer snapshots to capture data directories (requires write lock or consistent snapshot).
• Cold backup: Stop writes and copy data files for small deployments.
# Full backup of database
$ mongodump 
--db mydb --out /backups/mydb


# Restore entire database
$ mongorestore 
--db mydb --dir /backups/mydb


# Backup a single collection
$ mongodump 
--db mydb --collection users --out /backups/users


# Restore a single collection
$ mongorestore 
--db mydb --collection users --dir /backups/users
