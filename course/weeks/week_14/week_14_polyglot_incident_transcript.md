## Slide 2: A second database must earn its operating cost

A polyglot system uses different data technologies for distinct responsibilities. PostgreSQL might own users, permissions, and authoritative ticket state, while MongoDB stores a read-optimized ticket projection. The design is justified only when the workload benefit is concrete.

A second database also creates another credential, network path, schema or validator, query plan, monitoring surface, backup scope, and failure combination. A small system should prefer one suitable database when it can meet the workload. Choosing one platform is not less advanced. It can be the stronger engineering decision when cross-store consistency would add risk without measurable value.

## Slide 3: A transactional outbox gives the change one commit boundary

A naive synchronous dual write asks an application to update PostgreSQL and MongoDB as two separate remote actions. If the first succeeds and the second fails, the system disagrees. Reversing the order only reverses the partial-failure direction.

A transactional outbox writes the authoritative ticket change and an event row in the same PostgreSQL transaction. A relay later publishes that event, and a consumer updates the MongoDB projection. This removes the gap between committing the source fact and recording an event to publish. It does not guarantee exactly-once end-to-end behavior. The relay or consumer can retry, messages can arrive more than once or out of order, and the projection can lag.

## Slide 4: Delivery guarantees need stable identity and state transitions

At-least-once delivery means an event may be delivered more than once. If the consumer increments a value or appends a duplicate on every delivery, retries can corrupt the projection. A stable event identifier can detect duplicate processing, and a stable aggregate identifier can target the correct derived document.

Source versioning protects ordering. The consumer can apply an event only when its source version is newer than the version already stored. That turns duplicate and old deliveries into no-ops. Even then, progress records and reconciliation are required because a paused consumer or missing partition can leave derived state stale without producing a visible application error.

## Slide 5: Incident triage follows the fact across every boundary

Begin with the authoritative source. Query the ticket by stable identifier and record status, source version, and update time. Then inspect the outbox for the event generated by that same transaction. A published timestamp supports that the relay sent it, but it does not confirm downstream application.

Next inspect consumer logs or checkpoints for the stable event identifier. Finally, query the derived MongoDB document for source version and last event identifier. The first mismatch locates the propagation boundary. Do not stop after one record. Determine which queue, time window, tenant, or partition shares the same consumer state so verification covers the probable incident scope.

## Slide 6: The incident record locates one failed transition

PostgreSQL shows ticket 1008 resolved at source version 17. That is the authoritative state. The outbox contains event `evt-1008-17` and a published time, which rules out a missing source event. It does not confirm the consumer changed MongoDB.

The consumer received the event, timed out while writing the projection, queued a retry, and then paused because its database credential expired. MongoDB still contains version 16 and the previous event identifier. Together, these observations support a propagation failure after receipt. They do not support manually changing both databases or assuming only ticket 1008 is affected.

## Slide 8: A safe repair restores the path instead of inventing truth

The first repair should preserve the architecture's ownership rule. Restore the consumer's appropriately scoped database access, then replay the recorded event or resume the retry worker through the normal handler. The handler's version condition should apply version 17 once and ignore duplicate or older deliveries.

Manually changing both databases creates an untracked third path and can overwrite newer state. Replaying every event from the beginning creates unnecessary load and risk before the incident scope is known. Verification must cover the repaired record, retry queue, duplicate behavior, consumer lag, and a broader affected partition. If results are unexpected, pause the consumer and preserve the current state before making additional changes.

## Slide 9: The final project should remain understandable if a live demo fails

The second class turns incident discipline toward the final project. A cloud connection can fail during a demonstration because of network access, DNS, TLS, a paused service, an expired credential, or a local environment. If live success is the only demonstration, the presentation is fragile and the technical claim is underspecified.

A strong project includes prepared, redacted project material another person can inspect: schema or document shape, meaningful query output, an expected denial or invalid write, before-and-after plan output, backup artifact metadata, separate restore checks, and explicit limitations. Begin with the model. Another person should be able to state what one row or document represents, how identity works, how one relationship is represented, and which invalid state the database refuses. ## Slide 12: The outbox separates atomic commit from retryable delivery

A transactional outbox prevents a business row and its integration event from being committed through two unrelated operations. The application writes both records in one PostgreSQL transaction. A separate relay reads unpublished events and retries delivery. Because delivery may occur more than once, the MongoDB projection uses a stable event identifier or source version to make processing idempotent. Delivery state records whether an event is pending, attempted, or completed. During an incident, trace one stable identifier through authoritative commit, outbox row, relay attempt, consumer result, and projection version. Repair the normal path rather than manually inventing a second source of truth.

## Slide 13: Cross-database reliability begins with ownership and traceable events

This week showed why multiple databases multiply obligations. Every duplicated fact needs one authoritative owner, a propagation direction, acceptable lag, stable identity, idempotent handling, reconciliation, and recovery order. A transactional outbox closes one source-update gap, but delivery, retries, consumer credentials, lag, and verification still matter.

Incident response follows stable identifiers from authoritative commit through outbox, relay, consumer, and projection. A safe repair restores the normal path and verifies a broader scope. The final-project clinic applies the same principle: do not add features when one weak technical sequence threatens the whole claim. Next week we will synthesize the course and translate that work into portfolio and interview language.
