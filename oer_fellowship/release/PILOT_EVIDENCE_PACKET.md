# Pilot Evidence Packet

## Purpose and Current Boundary

This packet makes the rebuilt course ready for a responsible classroom pilot. It
defines what evidence to collect, how to interpret it, and how to connect a
revision to that evidence. It contains no invented results.

- **Candidate:** *Operating Cloud Databases*, version `1.0.0-rc.1`
- **Prepared:** August 9, 2026
- **Pilot state:** NOT STARTED
- **Student evidence in this packet:** none

The package may be described as authored, technically checked, and ready for
review. It must not be described as classroom-validated, student-tested, or
revised from learning evidence until the fields below are completed.

## Evaluation Questions

1. Do students recover enough relational-model, relational-algebra, and SQL
   reasoning in Weeks 1-3 to participate successfully in later operations work?
2. Can students produce evidence for a database claim rather than relying on a
   screenshot or unsupported assertion?
3. Can students transfer the same operating habits across PostgreSQL/Supabase and
   MongoDB/Atlas while recognizing where the models differ?
4. Do the local and static alternatives preserve learning when a cloud account,
   network, device, or vendor activity creates an access barrier?
5. Can students explain one technical decision, tradeoff, and limitation in
   career-connected language by the end of the course?

### Error-category vocabulary

- **Meaning:** incorrect grain, identity, relationship, or system boundary.
- **Mechanism:** incorrect SQL/MQL operator, transaction state, policy, plan,
  index, replication, or recovery mechanism.
- **Evidence:** missing baseline, identifier, observed result, expected failure,
  comparison, or limitation.
- **Transfer:** applies a relational rule mechanically to documents or treats two
  cloud interfaces as semantically identical.
- **Communication:** states a tool name or confidence claim without a technical
  decision, evidence, tradeoff, and scope.
- **Access/tooling:** account, network, browser, runtime, vendor, device, or
  accessibility barrier rather than a demonstrated concept error.

## Predetermined Instructional Decision Rules

- Below 70 percent correct on a core checkpoint: reteach with a different
  representation or worked example before adding complexity.
- 70-84 percent: use targeted retrieval plus a partially completed example.
- 85 percent or above: continue and schedule spaced retrieval.
- More than 15 percent blocked by access or tooling: use the equivalent open path
  and revise setup guidance before interpreting the result as learning evidence.
- A technically correct output with no reproducible evidence is incomplete; add
  an evidence checkpoint rather than more tool steps.
- Repeated completion without transfer calls for a contrasting case, not another
  identical exercise.

## Student Feedback Prompts

Use a small number of prompts that lead to actionable revision:

1. Which representation, example, or lab most changed how you reason about a
   database decision? Explain what became clearer.
2. Where did setup or platform behavior prevent you from showing what you knew?
3. Which task felt like authentic database work, and what made it feel authentic?
4. Which instruction or resource should be shortened, expanded, or represented
   differently for the next class?
5. What course artifact can you now explain in a job interview, and what evidence
   supports that claim?
