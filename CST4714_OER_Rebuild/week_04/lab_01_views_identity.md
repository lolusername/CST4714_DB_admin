# Lab 1: Build a Stable Query Interface

## Purpose

Create a useful view, inspect its definition, and observe how an identity column
generates identifiers independently from transaction success.

This is individual work completed in class. Submit one SQL file.

## 1. Create and Verify a View

Create `week_04_views_identity.sql`. Build
`metro_support.active_ticket_queue` with explicit columns for ticket ID, category,
priority, status, subject, opening time, and optional assignee name. Include only
`new`, `open`, and `in_progress` tickets.

Verify:

- the view row count equals a direct filtered base-table count;
- unassigned active tickets remain visible; and
- the view definition does not expose user email or event notes.

Query `information_schema.views` to inspect the stored definition.

## 2. Observe Identity Behavior

Create a small table named `metro_support.change_notes` with:

- `note_id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`;
- a non-null change name;
- a timestamp defaulting to `now()`.

Insert one committed row. Begin a new transaction, insert a second row with
`RETURNING note_id`, and roll it back. Insert another committed row.

Query the table and answer in a SQL comment:

- Are the committed identifiers consecutive?
- Why is a gap normal rather than corruption?
- Why should `max(note_id)` not be used as a row count?

## 3. Inspect the Objects

Use metadata queries to show the view, the identity column's default or identity
property, and the primary-key index on `change_notes`.

## Submit One Thing

Submit `week_04_views_identity.sql`. It should create the view and table, verify
the view, demonstrate the rolled-back identity allocation, and inspect the actual
objects.
