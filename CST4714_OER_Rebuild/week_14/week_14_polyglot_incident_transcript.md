## Slide 1: Polyglot Incident Response and Final Project Clinic

This week introduces polyglot persistence through an incident rather than a product tour. A system may use PostgreSQL for authoritative transactional facts and MongoDB for a read-optimized projection or flexible event detail. That can fit different workloads, but it creates synchronization, identity, observability, and recovery obligations.

Our resident portal and staff dashboard disagree about one ticket. You will investigate where the update stopped, choose a repair that respects ownership and idempotency, verify beyond one record, and write a concise workplace update. The second class applies the same evidence discipline to the highest-risk gap in your final project.

## Slide 2: A second database must earn its operating cost

A polyglot system uses different data technologies for distinct responsibilities. PostgreSQL might own users, permissions, and authoritative ticket state, while MongoDB stores a read-optimized ticket projection. The design is justified only when the workload benefit is concrete.

A second database also creates another credential, network path, schema or validator, query plan, monitoring surface, backup scope, and failure combination. A small system should prefer one suitable database when it can meet the workload. Choosing one platform is not less advanced. It can be the stronger engineering decision when cross-store consistency would add risk without measurable value.

## Slide 3: A transactional outbox gives the change one commit boundary

A naive synchronous dual write asks an application to update PostgreSQL and MongoDB as two separate remote actions. If the first succeeds and the second fails, the system disagrees. Reversing the order only reverses the partial-failure direction.

A transactional outbox writes the authoritative ticket change and an event row in the same PostgreSQL transaction. A relay later publishes that event, and a consumer updates the MongoDB projection. This removes the gap between committing the source fact and recording an event to publish. It does not guarantee exactly-once end-to-end behavior. The relay or consumer can retry, messages can arrive more than once or out of order, and the projection can lag.

## Slide 4: Delivery guarantees need stable identity and state transitions

At-least-once delivery means an event may be delivered more than once. If the consumer increments a value or appends a duplicate on every delivery, retries can corrupt the projection. A stable event identifier can detect duplicate processing, and a stable aggregate identifier can target the correct derived document.

Source versioning protects ordering. The consumer can apply an event only when its source version is newer than the version already stored. That turns duplicate and old deliveries into no-ops. Even then, progress records and reconciliation are required because a paused consumer or missing partition can leave derived state stale without producing a visible application error.

## Slide 5: Incident triage follows the fact across every boundary

Begin with the authoritative source. Query the ticket by stable identifier and record status, source version, and update time. Then inspect the outbox for the event generated by that same transaction. A published timestamp supports that the relay sent it, but it does not prove downstream application.

Next inspect consumer logs or checkpoints for the stable event identifier. Finally, query the derived MongoDB document for source version and last event identifier. The first mismatch locates the propagation boundary. Do not stop after one record. Determine which queue, time window, tenant, or partition shares the same consumer state so verification covers the probable incident scope.

## Slide 6: The evidence packet locates one failed transition

PostgreSQL shows ticket 1008 resolved at source version 17. That is the authoritative state. The outbox contains event `evt-1008-17` and a published time, which rules out a missing source event. It does not prove the consumer changed MongoDB.

The consumer received the event, timed out while writing the projection, queued a retry, and then paused because its database credential expired. MongoDB still contains version 16 and the previous event identifier. Together, these observations support a propagation failure after receipt. They do not support manually changing both databases or assuming only ticket 1008 is affected.

## Slide 7: Lab: Repair a stale MongoDB projection

Complete the incident lab individually from the supplied evidence packet. First build the timeline and distinguish observed facts from inference. Name PostgreSQL as the authoritative owner of ticket status, identify the committed version, confirm event creation and publication, locate the consumer failure, and compare the stored MongoDB version.

Recommend restoring the consumer credential and replaying or resuming the idempotent event path under the version rule. Include five verification checks and one containment or rollback action. Finish with a short incident update written for teammates and stakeholders. Avoid blame, unsupported certainty, and product marketing language. Submit one report containing every section.

## Slide 8: A safe repair restores the path instead of inventing truth

The first repair should preserve the architecture's ownership rule. Restore the consumer's appropriately scoped database access, then replay the recorded event or resume the retry worker through the normal handler. The handler's version condition should apply version 17 once and ignore duplicate or older deliveries.

Manually changing both databases creates an untracked third path and can overwrite newer state. Replaying every event from the beginning creates unnecessary load and risk before the incident scope is known. Verification must cover the repaired record, retry queue, duplicate behavior, consumer lag, and a broader affected partition. If results are unexpected, pause the consumer and preserve evidence before making additional changes.

## Slide 9: Final evidence should survive a failed live demo

The second class turns incident discipline toward the final project. A cloud connection can fail during a demonstration because of network access, DNS, TLS, a paused service, an expired credential, or a local environment. If live success is the only evidence, the presentation is fragile and the technical claim is underspecified.

A strong project includes prepared, redacted evidence another person can inspect: schema or document shape, meaningful query output, an expected denial or invalid write, before-and-after plan evidence, backup artifact metadata, separate restore checks, and explicit limitations. Today you will find the highest-risk missing part of that chain and complete it.

## Slide 10: Audit the project through one complete operating story

Begin with the model. Another person should be able to state what one row or document represents, how identity works, how one relationship is represented, and which invalid state the database refuses. Then show one meaningful read and one write tied to the workload, including expected and observed results.

Protection evidence should use the intended identity or rule and include an expected denial or invalid write, not just an administrator success. Operations evidence should cover a performance decision or recovery procedure with visible mechanism, verification, and limitation. The strongest next action is usually completing one missing evidence chain rather than adding another feature.

## Slide 11: Final project clinic: Finish the highest-risk evidence gap

Work individually from the canonical final-project page and rubric. Do not copy requirements from this slide into a new assignment and do not create a separate Week 14 submission. Audit the evidence you already have, then identify the one gap most likely to make your project claim hard to trust or demonstrate.

Complete that item in the existing project package. It may be a model explanation, expected-denial test, before-and-after plan, separate restore verification, or safe run order. Redact secrets and private account details. Prepare a static or recorded fallback for any cloud-dependent evidence. The purpose is depth and reliability, not adding last-minute scope.

## Slide 12: Cross-database reliability begins with ownership and traceable events

This week showed why multiple databases multiply obligations. Every duplicated fact needs one authoritative owner, a propagation direction, acceptable lag, stable identity, idempotent handling, reconciliation, and recovery order. A transactional outbox closes one source-update gap, but delivery, retries, consumer credentials, lag, and verification still matter.

Incident response follows stable identifiers from authoritative commit through outbox, relay, consumer, and projection. A safe repair restores the normal path and verifies a broader scope. The final-project clinic applies the same principle: do not add features when one weak evidence chain threatens the whole claim. Next week we will synthesize the course and translate that evidence into portfolio and interview language.
